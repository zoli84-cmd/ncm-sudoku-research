## 1. Label definition (unit-level / "substructure" probes)

- Units: "27 substructures: 9 rows, 9 columns, and 9 boxes" (Section 2, "Sudoku."; also Section 2 "A Sudoku puzzle is defined..." paragraph, which gives the exact set definitions `Row_r`, `Col_c`, `Box_k`).
- Label (243 probes = 27 units × 9 digits): **"Is digit d present in substructure S?"** — i.e., whether the digit is already *placed* (filled in) somewhere in that row/column/box, not whether it is still a *candidate*. Quote: "We train 243 binary linear probes that predict a global constraint: 'Is digit d present in substructure S?' (covering all 9 rows, 9 columns, and 9 boxes for each of the 9 digits)." (Section 3.2, "Are the candidates linearly represented in each substructure?")
  - Confirmed at the code level: `StructureMode.build_targets` in `sudoku/probes/modes.py:215-230` (commit `a9b206955`) builds `targets[i, d] = 1 if digit d+1 present in the substructure` by scanning the 9 cells of the row/col/box for a filled digit character — i.e., **presence of a placement**, not a derived "still a valid candidate somewhere in this unit" or "hidden single" label. Despite the subsection heading "Are the candidates linearly represented in each substructure?", the probe target itself is unit-level *digit-presence* (placement), and the paper explicitly distinguishes this from candidacy in the very next paragraph (see note below).
  - Note on terminology: the paper's own text flags the asymmetry — "If a digit is absent from the row, column, or box of a cell, it cannot be a candidate there, so substructure-absence linearly determines cell-candidacy. The converse does not hold..." (Section 3.2, paragraph after the main result). So their unit-level label is digit-*presence* (placed), and cell-level candidacy is a *downstream derived quantity*, not the thing probed at unit level. There is no separate "is there a hidden single for d in S" or "is d still a candidate somewhere in S" probe in the paper.
- Evaluation point in the solving trace: **primarily the `[clues_end]` token**, i.e., the initial puzzle state after all clues and before any generated placement — "The `[clues_end]` token serves as the primary anchor for our probing experiments: it follows all clue tokens and precedes any model-generated placement, providing a clean position at which to measure the model's representation of the initial board state." (Section 2, "Solving traces and model vocabulary.") "Unless otherwise stated, probes are trained on 5,120 puzzles from the test set and evaluated on 1,280, probing activations at the `[clues_end]` position after each layer." (Section 2, "Linear probing.")
  - They additionally test **persistence across later steps** (Section 3.4, second part, "Is the substructure-level representation persistent across solving steps?"): probes are trained once at `[clues_end]` and then *frozen* and evaluated (no retraining) at every later token position in the generation trace. Exact-match accuracy of the frozen probes degrades toward zero as the grid fills, but this is attributed to a shifting decision threshold (digit presence becomes near-universal as cells fill), not loss of linear encoding: ROC-AUC of the same frozen probes "stays at 1.0 across the entire trace for the mid-layers" (Section 3.4; Appendix B.3, Fig. 8).
  - Code confirms the per-step evaluation path: `ActivationIndex` in `sudoku/probes/session.py` indexes samples by trace `step` offset from the anchor (`step == 0` = `[clues_end]`), and `prepare_probe_inputs` in `sudoku/probes/probing.py:35-70` builds `probe_positions = [anchor_pos + step for ...]`, so the same `StructureMode.build_targets` is recomputed on the grid state at each queried step (`build_grid_at_step`, `sudoku/probes/activations.py:9-23`).

## 2. Probe input representation

- Representation: **residual stream activations** `x ∈ ℝ^{d_model}` (`d_model = 576`), taken after each of the 8 transformer layers (Section 2, "Model architecture and training." and "Linear probing."). The paper separately probes `post_attn` vs `post_mlp` activation types in the released code (`ProbeSession.__init__`, `act_type` parameter, `sudoku/probes/session.py:117-131`), though the main-text results use the post-MLP (standard per-layer) residual stream unless noted.
- Token position: **a single dedicated sequence position**, the `[clues_end]` token (or, for later-step variants, the position at that step offset from the anchor). This is a genuine special token inserted into the vocabulary, not one of the 81 cell positions — "The vocabulary consists of 729 placement tokens `[RrCc=d]` ... plus special tokens `[clues_end]` ... " (Section 2, "Solving traces and model vocabulary.").
- Unit-level readout: **no pooling over the unit's 9 cells**. The same single residual-stream vector at `[clues_end]` (one vector per puzzle, shared across all probe families) is the input `x` for every probe — the 81 cell-state probes, the 729 cell-candidate probes, *and* the 243 substructure probes all read out from this one position. Quote: "A linear probe ... for a binary concept f is a logistic regression classifier trained on residual stream activations x ∈ ℝ^{d_model}: P(f=1|x) = σ(w_f·x + b_f)." (Section 2, "Linear probing.", Eq. unnumbered display equation). Code: `get_activations_at_positions` (`sudoku/probes/activations.py:33-50`) does `acts = activations[idx, layer, pos]` — a plain fancy index extracting one `(d_model,)` vector per puzzle at one sequence position; there is no sum/mean/concat over the 9 cell positions of a row/column/box anywhere in `sudoku/probes/` or `plots/scripts/fig_*probe*.py`. The paper frames this explicitly as the finding: "it does not represent the board state cell by cell ... but organizes information around the rows, columns, and boxes" (Abstract) — i.e., the *linear direction itself*, not an explicit pooling operation, is what carries unit-level information into the single global residual vector.

## 3. Probe form, training, and reported numbers

- Form: logistic regression, `P(f=1|x) = σ(w_f·x + b_f)` (Section 2, "Linear probing."). For the 9-digit multi-label targets (both the 729 cell-candidate probes and the 243 substructure probes), the released code fits **9 independent per-digit binary logistic regressions** via `sklearn.multioutput.MultiOutputClassifier(LogisticRegression(C=1.0, max_iter=1000))` (`sudoku/probes/modes.py:25-26` `_make_lr`, `:36-39` `_fit_multilabel`, used by `StructureMode.fit` at `:232-233` and `CandidatesMode.fit` at `:196-197`) — i.e., not a single joint multi-label classifier, and no explicit L1/L2 weight beyond scikit-learn's default `C=1.0` (= inverse L2 regularization strength); no other regularization (dropout, weight averaging, etc.) is mentioned in the paper or code.
- Loss: standard logistic/cross-entropy loss implicit in scikit-learn's `LogisticRegression` solver; not separately named in the paper.
- Train/test split: **5,120 train / 1,280 test puzzles** (Section 2, "Linear probing."), i.e., an 80/20 split of 6,400 puzzles. Code: `sklearn.model_selection.train_test_split(..., test_size=0.2, random_state=42)`, used identically in `sudoku/probes/probing.py:122` (`probe_cell`), `:131` (`probe_structure`), and in the figure-generation script `plots/scripts/fig_probe_acc_by_layer.py:69` / `:79`. The split is over puzzles (not over the 27 units or 729 cell-digit pairs); every probe within a layer is fit/evaluated on the same held-out puzzle split.
- Metrics (defined explicitly in the code, consistent with the paper's figure captions):
  - **"Exact match"**: fraction of units (or cells) for which *all 9 per-digit binary predictions are simultaneously correct* — `exactmatch = float(np.mean(np.all(preds == y_test, axis=1)))` (`plots/scripts/fig_probe_acc_by_layer.py:56-62`, function `_accs_multilabel`). This matches the paper's Fig. 1 caption: "Green: 243 binary probes predicting if a digit is present in a substructure (exact match over a substructure)" (Fig. 1 caption, Section 3).
  - **"Element-wise" / per-label accuracy**: average 0.5-threshold binary accuracy over the 9 digits (`elementwise = float(np.mean(preds == y_test))`, same function).
  - **ROC-AUC**: per-digit AUC averaged over the 9 digits (`_eval_multilabel`, `sudoku/probes/modes.py:42-56`); used for the cross-layer/cross-step transfer analyses (Appendix B.1, B.3) because exact-match accuracy is sensitive to a shifting decision threshold as the grid fills (Section 3.4).
  - Brier score / MSE between predicted probability vectors and one-hot/multi-hot targets is also reported (Appendix B.1, Fig. 6).
- Reported numbers:
  - **Substructure probes (243, unit-level)**: "perfect exact match accuracy across all 243 (substructure, digit) pairs in mid-layers" (Section 3.2; repeated in Conclusion as "near-perfect accuracy ... from mid-layers onward"). AUC ≈ 1.0 from layer 4 onward and remains so through layer 8 (Appendix B.1, Fig. 6 right panel; Section 3.4 persistence experiment, Appendix B.3 Fig. 8 right panel — AUC ≈ 1.0 for L4–L7, dipping to ≈0.98 only for L8 mid-trace).
  - **Per-cell candidate probes (729)**: "achieve 1.0 exact match accuracy through layers 4 to 6" but then "deteriorate sharply at L8" (Section 3.1 "Are the candidates linearly represented in each cell?"; Fig. 1 left, Fig. 6 caption). Unlike the substructure probes, their exact-match/AUC score is not stable at the final layer.
  - **Per-cell *filled-digit* probes (81, not "candidate" — the literal digit occupying the cell)**: accuracy peaks at 0.8 after layer 4 and plateaus there through layers 5–7 (Section 3.1 "Are the contents of cells linearly represented?"; Conclusion: "per-cell probes plateau at 0.8"). This is the 81-probe family (`FilledMode`/`StateFilledMode` in code), distinct from the 729 per-cell candidate probes — be careful not to conflate "per-cell probe = 0.8" (filled-digit identity) with "per-cell candidate probe = 1.0 in mid-layers" (candidacy) when comparing to the unit-level 243-probe result.
  - Layer-transition: a "sharp phase transition at layer 4" in a cross-layer transfer experiment (probes trained at one layer, evaluated at another without retraining): probes trained on layers 1–3 fail to transfer to later layers; probes trained on layers 4–7 transfer near-perfectly across the whole mid-layer span (Section 3.4, Fig. 2 left).
  - Causal check (not a probe metric but supports "actually used"): patching the 3 relevant substructure-probe directions (row, column, box for the target placement) into a different grid state drops the target placement's logit by up to ≈25 (peak at layer 4) and changes the model's top-1 prediction in 99% of cases (Section 3.3, Eq. 1; Table 4 in Appendix B.4).

## 4. Per-cell candidate label definition (for comparison with our 9-bit initial candidate mask)

Quote: "each probe answers 'If cell (r,c) is empty, is digit d a valid candidate in it?'" (Section 3.1, "Are the candidates linearly represented in each cell?"). Formal definition in Section 2: "The candidate set cand(r,c) = {1,...,9} \ (digits in Row_r ∪ Col_c ∪ Box_k) collects all valid digits for an empty cell." (Section 2, "Sudoku.")

Code implementation, `cell_candidates` in `sudoku/probes/modes.py:59-77`: for an empty cell `(r,c)`, scans the 9 cells of its row and the 9 cells of its column (loop `for j in range(9)`, reading `puzzle[r*9+j]` and `puzzle[j*9+c]`) and the 9 cells of its 3×3 box, collects the set of digits already present (`used`), and returns a 9-element binary vector `[1 if d not in used else 0 for d in 1..9]`.

This is **the same definition as ours**: a 9-bit mask over digits 1–9 for each empty cell, where bit d = 1 iff digit d does not appear among the cell's row/column/box peers (their row+column+box peer set has 8+8+4=20 distinct cells for a cell not in the box's row/column overlap-adjusted count — standard 20-peer Sudoku definition, matching our "20 peers" framing even though the paper phrases it as "row ∪ column ∪ box" rather than literally "20 peers"). One difference worth flagging: their `build_targets` for `CandidatesMode` (`sudoku/probes/modes.py:184-189`) computes this mask **from the grid state at the probed step** (i.e., it is recomputed at whatever point in the trace the probe is evaluated, using partially-filled grids for later steps), not only from the initial puzzle's clues. For the `[clues_end]` evaluation point specifically (step 0), this reduces to exactly "digits not present among the cell's peers in the initial clue grid," matching our candidate-mask definition on the initial puzzle state.

## 5. What makes direct comparison problematic

- **Model and training regime are task- and architecture-specific**: 8-layer, 8-head, `d_model=576`, `d_mlp=3456` (6× expansion) decoder-only transformer, trained on 2.7M puzzles from the `sudoku-3m` Kaggle dataset with Norvig-style backtracking solving traces (clues → deductions → `[push]`/`[pop]` backtracking → `[success]`), traces trimmed to 250 tokens, 6 epochs, AdamW, lr 1e-3 (Section 2 "Model architecture and training."; Appendix A.1–A.2). A different model/architecture/training-trace format (e.g., NCM's coarse-to-fine residual-token generation rather than autoregressive placement-token traces) will not have a `[clues_end]`-equivalent anchor token unless one is constructed, and may not have the same layer count or mid-layer "phase transition" structure.
- **Unit-level label is placement-presence, not candidacy or hidden-single**: if "our project" intends to probe for something like "is d still a *candidate* somewhere in unit u" or "does u have a hidden single for d," that is **not** what this paper's 243 substructure probes measure — theirs is literally "has d already been placed in u," which is a much easier/more directly supervised signal (computable from the current grid alone, no search needed) and is logically antitonic to (but not identical to) a "candidate present in unit" label. Replicating "candidate-level" unit probes as the paper's benchmark would be a label mismatch.
- **Probe readout is single-position, whole-puzzle, not per-cell-pooled**: their claim of "substructure organization" is inferred from the *linear direction* recoverable from one global residual vector, not from an explicit architectural pooling step over the unit's 9 cells. If the comparison project's model does not have an equivalent single "end of clues" anchor token (e.g., it emits per-cell or per-unit tokens, or encodes the grid via positions with a different token budget), there is no off-the-shelf equivalent position to probe, and a pooling scheme would need to be newly defined and is not validated by this paper.
- **Exact-match accuracy is sensitive to class-balance drift across the trace**: the paper explicitly shows that evaluating frozen `[clues_end]`-trained probes at later trace steps drives exact-match accuracy toward zero as a thresholding artifact (near-saturated positive rates), while AUC remains ≈1.0 (Section 3.4; Appendix B.3). Any cross-paper comparison of "exact match" numbers at different points in solving must control for how filled the grid is at evaluation time, or compare AUC instead.
- **Dataset/puzzle-count scale differs by experiment**: the headline 243-probe result uses 5,120/1,280 train/test puzzles (Section 2), but other analyses in the paper use different puzzle counts (e.g., 300 grid pairs for the causal-patching experiment in Section 3.3; 6,400 puzzles for the attention-head analysis in Section 4; 1,280 held-out puzzles for the head-ablation experiment in Section 4.3) — "the" reported accuracy is not from one single fixed evaluation set across all figures/tables, so care is needed in matching which number is being replicated.
- **GitHub username/author mismatch is unresolved** (see top of this document) — **unverified** whether `kameronton` is one of the two listed authors (Roman Kniazev, Nathanaël Fijalkow) under a pseudonym/lab account, a co-author not listed on arXiv, or an unrelated maintainer; this does not affect the technical content but is worth noting if citing repository provenance.
- **No release tag/version pin in the repo**: the repository has no tags as of the fetch date; the commit hash `a9b206955bfd1089a7253511fa9371066ecca570` (HEAD, dated 2026-05-06T20:57:42Z per the GitHub API) is the only stable anchor used for the `file:line` citations above, and the code could change if the repo is updated after this date — re-verify before relying on exact line numbers. On 2026-11-23 it was still the latest commit.

The released artifacts (checkpoint step 25452, configs, training log, probing-set metadata, `bt_traces_3m.npz`) are at <https://huggingface.co/datasets/residual-sudoku-dataset/residual-sudoku-dataset> (MIT); provenance in `experiments/provenance/kf_artifacts.json`.
